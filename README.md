# За столом — банкет с выбором каждого гостя

Организатор создаёт мероприятие и делится приглашением. Гости выбирают блюда из меню ресторана, организатор проверяет общую сумму и утверждает заказ. Ресторан получает количества и индивидуальные пожелания в своём интерфейсе и CSV.

Репозиторий: [Ja1rman/max-hackathon](https://github.com/Ja1rman/max-hackathon). Опубликованная демонстрация: [mail.lonelycraft.ru/banquet/](https://mail.lonelycraft.ru/banquet/). HTTPS-демонстрация развёрнута и проверена 16 сентября 2026 года; токен бота @t266_hakaton_max_bot проверен через официальный MAX API. Для проверки настоящего входа внутри MAX владелец должен привязать URL Mini App в настройках бота.

## Возможности

Во вкладке «Доступы» видны только участники доступных банкетов и пользователи с правами в доступных ресторанах. Администратор сервиса назначает администраторов ресторанов; организатор банкета или администратор ресторана назначает других организаторов именно на этот банкет. Можно добавить человека по MAX ID или номеру телефона; назначение по телефону активируется после подтверждения номера через MAX. Создатель банкета автоматически становится организатором. Организатор управляет всем банкетом, включая утверждение, но не видит ресторанные вкладки «Рестораны» и «Кухня». Каждый человек с правами может быть гостем другого банкета.

Во вкладке «Рестораны» администратор настраивает залы, вместимость, недельные окна бронирования и рассадку: готовую карту столов и стульев либо набор размеров столов, из которого организатор собирает схему. При готовой карте организатор выбирает, будут ли гости занимать места сами, он назначит их лично или рассадка не нужна; двигать столы он не может. Настройки копируются в новые банкеты и не меняют уже созданные. Дату и время банкета выбирают в мини-календаре свободных слотов. Банкеты бронируют зал на фиксированное число часов; пересечение броней одного зала отклоняется сервером. Ресторан «Петръ» содержит меню из предоставленных фотографий, тестовые блюда размещены в «Temp». Пакет собирается из отдельных блюд с фото и КБЖУ; гость видит состав и может выбрать место даже в фиксированном пакете. В «Кухне» можно выгрузить один или несколько выбранных банкетов; Excel содержит порции, гостей, рассадку и пакеты.

- Администратор ресторана: настройки залов, окна бронирования и меню ресторана со стоимостью, составом, КБЖУ и аллергенами; раздел «Кухня» со сводкой по всем запланированным банкетам и выгрузкой в Excel (XLSX) или CSV; банкеты своих ресторанов с организатором, заказами гостей, блюдами и рассадкой; настройка рассадки и меню любого банкета; утверждённый заказ и экспорт CSV.
- Организатор: название, дата, срок ответа, число гостей и **бюджет на одного гостя**; список приглашённых с именами и телефонами; какие позиции меню ресторана доступны гостям (с добавлением из каталога); **блюда и закуски на общий стол**; схема рассадки; собственный выбор блюд и места; сумма и утверждение. Дополнительного организатора можно назначить в «Доступах» по телефону или MAX ID.
- Гость: выбор только за свой подтверждённый через MAX номер; новые приглашения на этот номер появляются автоматически. По персональной ссылке гость может войти, даже если номер заранее не внесли; подписанное подтверждение MAX создаст его собственную запись. Меню содержит фото, состав, КБЖУ, аллергены, напитки и фильтры пометок.
- Внутренняя валюта: гость не видит рубли. Еда стоит **кусочки пирога** 🥧 (1 = 10 ₽), напитки (категория «Напитки») — **бутылочки** 🍾 (1 = 100 ₽); это независимые валюты, значения показываются иконками, дробные — как есть. Организатор задаёт на гостя два бюджета в рублях — на еду и на напитки, каждый является жёстким лимитом.
- Рассадка (по желанию): схема зала из круглых и прямоугольных столов с шаблонами (круглые столы, П-образная, с президиумом, Т-образная, длинный стол), перетаскивание и переименование столов, число стульев за каждым столом. Гости выбирают свободное место или получают его от организатора и видят имена тех, кто уже сидит на местах; оставшихся без места сервис рассаживает автоматически при утверждении.
- MAX: сервер проверяет подписи `initData` и `requestContact()`; приглашения поддерживают `startapp`; по согласию пользователя бот отправляет уведомления и напоминания.
- HTTP API: создание и редактирование банкетов, гостей, позиций меню, загрузка фото, подтверждение номера и настройки уведомлений описаны в [OpenAPI](openapi.yaml) и [руководстве API](docs/API.md).
- Демо: отдельное пространство данных для каждой новой демо-сессии, четыре роли (администратор сервиса, администратор ресторана, организатор и гость), два банкета и синтетические гости на базе каталога «Петръ».

Во всех 172 позициях «Петръ» и 12 тестовых позициях «Temp» есть иллюстративные фото; источники и лицензии сторонних снимков опубликованы на странице [атрибуции фотографий](public/petr-photos/credits.html). Фото показывают тип блюда и могут отличаться от фактической подачи. Рестораны можно искать и добавлять в личное избранное, а организатор может удалить свой банкет.

## Быстрый запуск через Docker

Нужны Docker Engine/Desktop и Docker Compose v2. Скопируйте настройки:

```sh
cp .env.example .env
```

Настройки `.env.example` уже подходят для локального Docker: `PUBLIC_URL=http://localhost:3100` и `VITE_BASE_PATH=/`. Пустые поля MAX оставьте пустыми для демо. После подготовки `.env` приложение собирается и запускается одной командой:

```sh
docker compose up -d --build
```

Откройте [localhost:3100](http://localhost:3100). Контейнер слушает порт 3000, порт хоста 3100 привязан только к `127.0.0.1`. SQLite сохраняется в томе `banquet_data`, отдельно от образа. `docker compose restart` сохраняет данные. Остановка: `docker compose down` без `-v`, чтобы сохранить том.

## Разработка без Docker

Нужны **Node.js 24+** и npm. База использует встроенный `node:sqlite`; отдельный сервер СУБД и runtime npm-зависимости backend не требуются. Frontend — React 19.1.1, Vite 7.3.6 и Lucide.

```sh
npm ci
```

Запустите API и frontend в двух терминалах:

```sh
PUBLIC_URL=http://localhost:5173 npm run dev:api
```

```sh
npm run dev
```

Vite открывается на [localhost:5173](http://localhost:5173), проксирует `/api` и `/healthz` на API `127.0.0.1:3000`. `npm run dev:api` и `npm start` автоматически `.env` не читают: задайте переменные окружения либо используйте `node --env-file=.env server/index.mjs`.

Для одного процесса с собранным интерфейсом:

```sh
npm run build
PUBLIC_URL=http://localhost:3000 npm start
```

Откройте [localhost:3000](http://localhost:3000). Локальная сборка по умолчанию использует корневой путь `/`; Docker по умолчанию также использует `/`. Для production в серверном `.env` задаются `VITE_BASE_PATH=/banquet/` и `PUBLIC_URL=https://mail.lonelycraft.ru/banquet`; nginx удаляет префикс при проксировании.

## Правила заказа и данных

При создании банкета сервер копирует доступные блюда из каталога в **снимок меню**. Изменение цены или доступности в каталоге относится к новым банкетам; существующий заказ использует свой снимок. Все цены, бюджет и суммы JSON API — **целые копейки**. Клиент передаёт идентификатор блюда и количество; цену и сумму вычисляет сервер.

Заказ начинается в `collecting`. После дедлайна нельзя присоединяться новым гостям и менять выбор, но статус остаётся `collecting`, пока владелец не утвердит заказ. Утверждение переводит его в `approved`, фиксирует `approvedAt` и закрывает изменения. Нужен минимум один ответ; дожидаться всех приглашённых необязательно. Бюджеты на еду и на напитки задаются на одного гостя и являются независимыми жёсткими лимитами: сервер отклоняет более дорогой выбор. Общий стол оплачивает организатор, в бюджет гостей он не входит. Утверждение банкета бюджетом не блокируется. Число ожидаемых гостей — план; список приглашённых можно вести из админки или API, технический предел — 1000 участников. Для live-банкета гость должен передать подписанный MAX результат `requestContact()`; по персональной ссылке номер связывается с собственной записью, даже если организатор не внёс его заранее. Ссылка сама по себе не даёт права выбирать блюда. Демо-приглашения остаются отдельным тестовым сценарием.

Для защиты от изменения суммы между просмотром и подтверждением API требует `expectedRevision` для ещё открытого заказа: если гость изменил выбор, сервер возвращает 409 и просит обновить заказ. Повторное утверждение уже утверждённого заказа возвращает текущее состояние. Отмена, повторное открытие и удаление заказа пока не реализованы.

Гость видит только собственные позиции и пожелания. Организаторы банкета и администраторы ресторана видят все ответы банкета. Администратор ресторана видит банкеты только своего ресторана; глобальный администратор — всех ресторанов. Уведомления MAX пользователь включает в «Профиле» через кнопку в правом верхнем углу или на странице банкета; в профиле также выбирает категории сообщений. Боту нужен открытый чат с пользователем.

Каждый новый вход в демо создаёт отдельный `scope`. Переключение ролей доступно только внутри той же демо-сессии. Демо-гость по ссылке не получает права организатора; доступ к live-данным из демо запрещён. Демо-сессия авторизации действует сутки, live-сессия — семь суток. Демо-пространства и ключи дедупликации webhook удаляются спустя семь суток при обслуживании базы. Одновременно разрешены 10 сессий на пользователя; новая сессия вытесняет самые старые. `DEMO_ENABLED=false` отзывает существующие демо-сессии и скрывает демо-приглашения. Для live-заказов автоматическое удаление не предусмотрено.

## Проверка сценария

```sh
npm run check
```

Команда выполняет backend-тесты и production-сборку. Проверки MAX используют искусственно подписанные данные и mock API; успешные тесты не подтверждают фактическую регистрацию бота.

1. Откройте демо организатора: синтетический банкет содержит 12 ожидаемых гостей, 6 присоединившихся и 5 готовых ответов. Создайте также собственный банкет с будущими датой и дедлайном.
2. Скопируйте приглашение и откройте в отдельном браузерном профиле. Войдите гостем, сохраните блюда и пожелания. Обновите страницу: выбор должен сохраниться.
3. Вернитесь организатором, обновите заказ и проверьте сумму и ответ гостя. Перед утверждением оцените плановый бюджет и неответивших гостей, затем подтвердите заказ.
4. В демо переключитесь на ресторан. Откройте утверждённый банкет, сравните сводку и CSV. Измените цену блюда в каталоге: цена в старом банкете должна остаться прежней.
5. Вернитесь гостем: после утверждения выбор закрыт. Попробуйте старую ревизию через API на ещё открытом банкете после изменения гостем: ожидается 409.
6. Создайте новую демо-сессию в другом браузерном профиле: первый банкет в ней не должен быть доступен. Перезапустите сервер и проверьте сохранение данных первой сессии.

Тестовые имена, блюда и ресторан вымышлены для демонстрации. Файл [fixtures/demo.json](fixtures/demo.json) описывает стартовый набор без действующих токенов и приглашений; backend создаёт его программно, автоматический импорт файла не выполняется.

## MAX и поставка

Бот проекта — [@t266_hakaton_max_bot](https://max.ru/t266_hakaton_max_bot). Токен, username и ресторанный MAX ID настроены через GitHub Secrets. Привязка Mini App URL в настройках бота ожидает доступа от организаторов хакатона; пока её нет, проверить вход и запрос телефона на настоящем устройстве невозможно. Подробности — [docs/MAX.md](docs/MAX.md).

GitHub Actions проверяет pull request и выполняет те же проверки перед deploy из `main`. Deploy упаковывает отслеживаемый Git код, передаёт его по SSH, собирает образ на сервере, делает согласованную копию SQLite, проверяет здоровье и переключает релиз. В репозитории настроены `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`: push в `main` запускает автоматический deploy после проверок. Приватный ключ хранится только в GitHub Actions Secret; на сервере установлена его публичная часть. Если какой-либо секрет удалён, deploy явно пропускается с пояснением в GitHub Actions Summary. [Инструкция развёртывания и отката](docs/DEPLOYMENT.md).

## Границы MVP

Каталог при первом запуске содержит демонстрационный ресторан даже в live-пространстве: сотрудник должен заменить пример фактическим меню и проверить КБЖУ перед заказами. Нет оплаты, интеграций с кассой/CRM, подтверждения принятия заказа рестораном и времени подачи. Схема зала задаётся для каждого банкета отдельно; общего сохранённого плана зала ресторана пока нет. Пожелания и аллергены — сведения для согласования с рестораном, без автоматической гарантии безопасности блюда. Редактирование каталога не меняет снимки уже созданных мероприятий; меню отдельного банкета теперь можно править до утверждения с защитой уже выбранных блюд.

API отдаёт CSV после утверждения. Для загрузки через MAX Bridge предусмотрена отдельная одноразовая HTTPS-ссылка сроком 60 секунд; её использование на настоящем устройстве нужно проверить после подключения бота. Сервис развёртывается одним экземпляром с SQLite: масштабирование на несколько серверов требует отдельной архитектуры хранения. Резервные копии в том же Docker-томе не защищают от потери диска; внешнее хранение нужно настроить отдельно.

## Проверка опубликованного релиза

`SMOKE_BASE_URL=https://mail.lonelycraft.ru/banquet node scripts/smoke.mjs` проверяет полный API-сценарий только в новом изолированном демо-пространстве. Нужен `DEMO_ENABLED=true`; реальные данные не затрагиваются.
