# API сервиса «За столом»

Базовый адрес API: **`https://mail.lonelycraft.ru/banquet/api/v1`** — все пути ниже указаны относительно него (например, `GET /me` → `https://mail.lonelycraft.ru/banquet/api/v1/me`). Машиночитаемая схема: [openapi.yaml](../openapi.yaml), она же опубликована по адресу `https://mail.lonelycraft.ru/banquet/openapi.yaml`; интерактивная документация Swagger UI — `https://mail.lonelycraft.ru/banquet/swagger/`. Как получить тестовые учётные записи и пройти обязательные проверки, описано в [TESTING.md](TESTING.md) и [DATA-API.yaml](../DATA-API.yaml). Запросы с JSON отправляйте с `Content-Type: application/json`; все цены и суммы передаются **в целых копейках**, даты — ISO 8601 с часовым поясом. Ошибки имеют вид `{"error":"..."}`. Идентификаторы берите из ответов API.

## Вход и роли

В Mini App передайте исходную строку `window.WebApp.initData` в `POST /auth/max`:

```json
{"initData":"<строка MAX Bridge>"}
```

Ответ содержит `token` сервиса и `user`. Во всех защищённых запросах используйте `Authorization: Bearer <token сервиса>`. **Токен бота MAX для этого не подходит и никогда не отправляется из браузера.** Для локальной проверки можно войти через `POST /auth/demo` с `{"role":"organizer"}`; демо-данные изолированы и не имеют доступа к реальным банкетам.

Доступ выдаётся по ресторанам. `GET /me` возвращает `maxId`, `access: [{restaurantId, restaurantName, role}]` (`admin` или `organizer`), `superAdmin`, `botConnected` и сводную роль `role`: `admin` для глобального администратора из `RESTAURANT_ADMIN_IDS`, `restaurant` для администратора конкретного ресторана, `organizer` или `guest`. Глобальный администратор создаёт рестораны через `POST /restaurants` и назначает их администраторов. `PATCH /restaurants/{id}` меняет данные ресторана его администратор. `GET /users?q=<имя, телефон или MAX ID>` показывает пользователей, открывавших приложение; `GET /restaurants/{id}/members` — назначенные роли ресторана. `PUT /restaurants/{id}/members/{userId}` с `{"role":"admin"|"organizer"|"none"}` принимает ID из списка пользователей или числовой MAX ID, в том числе до первого входа человека. `DELETE` снимает роль. Администратор ресторана может назначать и снимать только организаторов своего ресторана; роль администратора ресторана назначает и снимает только глобальный администратор. Создать банкет можно только в ресторане, где есть роль. Управлять им могут владелец с действующей ролью и администраторы ресторана (`event.canManage`); бывший владелец сохраняет просмотр, но не управление. **Утвердить заказ может только владелец с действующей ролью**. Пользователь с любой ролью может быть гостем. `OPEN_ORGANIZER_SIGNUP=true` включает открытый тестовый набор организаторов; в production он выключен.

## Создание банкета и список гостей

Глобальный администратор может выдать такую же роль другому MAX-пользователю через `PUT /admins/{userId}` с `{"enabled":true}` или снять её с `{"enabled":false}`. Вместо `userId` принимается числовой MAX ID; пользователь может ещё не открывать приложение. Назначенный администратор получает доступ ко всем ресторанам. Снять собственную роль или роль, закреплённую в `RESTAURANT_ADMIN_IDS`, нельзя. Роли можно назначать в интерфейсе «Доступы».

`GET /restaurants` возвращает доступные рестораны с полями `menu` и `packages`. Каталог ресторана «Петръ» и три пакетных предложения создаются при миграции v10. Цены и граммовки переписаны из предоставленных фотографий; КБЖУ — ориентировочная оценка, которую ресторан должен проверить. Пакет редактируется администратором ресторана: `POST /restaurants/{restaurantId}/packages`, `PATCH` или `DELETE /restaurants/{restaurantId}/packages/{packageId}`. Тело для создания: `{"name":"Пакет 4500","description":"...","price":450000,"items":[{"category":"Закуски","name":"Лосось","grams":20}]}`. Цена указана в копейках за гостя, граммы — на гостя. Состав существующего банкета хранится снимком и не меняется при правке каталога.

1. `GET /restaurants` — получить рестораны и их текущий каталог.
2. `POST /events` — создать банкет. Тело: `restaurantId`, `title`, `date`, `deadline`, `expectedGuests`, необязательные `foodBudget`, `drinkBudget` и `photoUrl`. Бюджеты одного гостя на еду и на напитки задаются в копейках (0 — без ограничения). `photoUrl` берётся из `POST /media`. Сервер создаёт снимок доступных блюд.
   Для фиксированного заказа добавьте `"selectionMode":"package"`, `"packageId":"package_..."` и, если пакет включает альтернативы горячего, `"packageChoice":"название блюда"`. По умолчанию действует `"selectionMode":"individual"`. В пакетном режиме гость видит состав, но `canSelect=false`; итог равен цене пакета × числу гостей плюс общий стол. Утвердить пакет можно без гостевых заявок.
3. `PATCH /events/{eventId}` — изменить название, дату, срок выбора, число гостей, бюджеты или фото. Пустая строка `photoUrl` убирает фото. Передайте `expectedRevision` из последнего `GET /events/{eventId}`. При устаревшей ревизии получите `409` и должны перечитать данные.
4. `POST /events/{eventId}/guests` с `{"name":"Анна","phone":"+7 999 123-45-67"}` — добавить гостя. `PATCH` и `DELETE /events/{eventId}/guests/{guestId}` — изменить или удалить запись. Телефон нельзя поменять после привязки к MAX; гостя с сохранённым выбором удалить нельзя.
5. `GET /events/{eventId}` — владельцу и ресторану вернёт `invitedGuests`, `guests`, `summary` и ссылки приглашения. Телефоны не включены в публичный просмотр по ссылке и в ответ чужому гостю.

Число гостей — ориентир для интерфейса; при добавлении записи список может увеличить `expectedGuests`. Все изменения разрешены до утверждения. После утверждения состав заказа фиксируется. По персональной ссылке может войти и человек, которого организатор не добавил заранее: после подтверждения номера через MAX сервис создаёт его собственную запись. Ссылка не даёт права выбрать чужие блюда.

## Подтверждение гостя и заказ

Гость входит через MAX и разрешает `window.WebApp.requestContact()` в нативном окне. Результат `{phone, authDate, hash}` передаётся в `PUT /me/phone`. Сервер проверяет подпись MAX с токеном бота и связывает номер с проверенным MAX ID из сессии. Подменить `userId` параметром запроса нельзя. При открытии **общей кнопкой бота** Mini App автоматически вызывает `POST /me/claim-invitations` для уже подтверждённого номера и показывает новые банкеты; отдельная кнопка поиска не требуется. При персональной ссылке Mini App запрашивает номер, если он ещё не подтверждён, затем вызывает `POST /invites/{code}/join`. Один номер не может быть привязан к двум аккаунтам; одна запись банкета не может принадлежать двум гостям.

`GET /events/{eventId}` возвращает меню, `canSelect` и собственный `selection`. `PUT /events/{eventId}/selection` полностью заменяет выбор текущего пользователя:

```json
{
  "items": [{"menuItemId":"dish_...","quantity":2}],
  "notes":"Без орехов"
}
```

Организатор-владелец тоже может выбрать блюда (и место при режиме `choice`) для себя без записи в списке гостей; его выбор входит в общий заказ. Цена и сумма вычисляются сервером из меню банкета. Если блюда дороже `event.foodBudget` или напитки (категория «Напитки») дороже `event.drinkBudget`, сервер вернёт `409`; неиспользованный бюджет на еду не переносится на напитки и наоборот. Позиции с `forGuests: false` и позиции общего стола выбрать нельзя (`400`). Гость не может передать ID другого пользователя. После дедлайна или утверждения изменения блокируются. `POST /events/{eventId}/approve` с `{"expectedRevision":12}` утверждает текущую версию. Для кухни доступны `GET /events/{eventId}/export.csv` и одноразовая ссылка `POST /events/{eventId}/export-link`.

## Меню банкета и общий стол

Меню банкета — снимок каталога. У каждой позиции есть флаг `forGuests`: `PATCH /events/{eventId}/menu/{itemId}` с `{"forGuests":false}` скрывает её от гостей (гостям такие позиции не отдаются). Позицию, которую уже выбрал гость, скрыть нельзя. `POST /events/{eventId}/menu/import` с `{"itemIds":["dish_..."]}` добавляет позиции каталога ресторана, которых ещё нет в банкете.

`PUT /events/{eventId}/shared` задаёт общий стол целиком:

```json
{"items": [{"menuItemId":"dish_...","quantity":3}]}
```

Позиции общего стола входят в `event.total` и сводку кухни, но не в бюджет гостя. Гости видят их в `detail.shared` и не могут заказать сами. Позицию, которую уже заказал гость, на общий стол перенести нельзя.

## Внутренняя валюта гостя

API всегда работает в копейках; пересчёт делает интерфейс гостя (`shared/currency.mjs`). Это две независимые валюты: еда стоит кусочки пирога 🥧 (1 = 10 ₽), позиции категории «Напитки» — бутылочки 🍾 (1 = 100 ₽). Интерфейс показывает значения иконками, дробные значения не округляются до целых. Бюджет гостя отображается двумя шкалами: еда в кусочках, напитки в бутылочках.

## Администратор и кухня

`GET /kitchen` возвращает банкеты ресторанов, где пользователь — администратор, с датой не раньше вчерашнего дня: `event` (с `ownerName`), порции `summary` с учётом общего стола, `shared`, `seating` и гостей с выбором, пожеланиями и местом. Владелец и администратор также получают `event.ownerName`, `event.sharedTotal` и плановый `event.budget = (foodBudget + drinkBudget) × expectedGuests`. `GET /kitchen/export?format=xlsx|csv&eventIds=event_...,event_...` выгружает выбранные мероприятия; для загрузки внутри MAX используйте `POST /kitchen/export-link` с `{"format":"xlsx","eventIds":["event_...","event_..."]}` и `WebApp.downloadFile`. Передавать можно от 1 до 100 доступных ID. Без `eventIds` API выгружает все доступные мероприятия. Excel содержит листы «Порции», «Гости», «Рассадка» и «Пакеты»; CSV содержит те же блоки.

## Рассадка

Рассадка необязательна: по умолчанию `seating.mode` равен `off`, и банкет собирает только блюда. `GET /events/{eventId}` всегда возвращает объект `seating` со схемой зала, режимом, списком занятых мест `occupied` и собственным местом `mySeat`. Владелец и ресторан дополнительно получают `people` — всех гостей с их местами — и поле `seat` у каждого гостя.

`PUT /events/{eventId}/seating` включает рассадку и сохраняет схему целиком:

```json
{
  "mode": "choice",
  "layout": {"tables": [
    {"id":"t1","shape":"round","label":"1","x":60,"y":60,"w":120,"h":120,"rotation":0,"seats":8},
    {"id":"t2","shape":"rect","label":"Президиум","x":300,"y":60,"w":300,"h":70,"rotation":0,"seats":5,"sides":["top"]}
  ]}
}
```

Режимы: `off` — без рассадки, `choice` — гости выбирают места сами, `fixed` — места назначает организатор. Стулья не передаются: их номера и координаты вычисляются из стола, id места имеет вид `<tableId>-<n>`, нумерация идёт по часовой стрелке. Готовые шаблоны (круглые столы, П-образная, с президиумом, Т-образная, длинный стол) строит функция `generateLayout` из `shared/seating.mjs`. Сохранить схему, в которой пропадает уже занятое место, нельзя: сервер вернёт `409` и перечислит такие места.

Гость выбирает место через `PUT /events/{eventId}/seat` с `{"seatId":"t1-3"}`, а `{"seatId":null}` освобождает его. Если место уже занято, сервер вернёт `409`. Организатор назначает места через `PUT /events/{eventId}/seating/assignments` с `{"guest":"invite:...","seatId":"t2-1"}`; `guest` берётся из `seating.people[].key`. Если место занято, гости меняются местами. Любой участник банкета видит в `seating.names` имена гостей на занятых местах (`{"t1-2":"Мария"}`); телефоны и полный список гостей получают только владелец и администратор (`seating.people`). `POST /events/{eventId}/seating/auto` рассаживает всех гостей без места: сначала за столы, где уже кто-то сидит, затем за пустые. То же происходит автоматически при утверждении заказа. После утверждения рассадка фиксируется, а CSV получает колонку «Место» и отдельный блок «Стол / Место / Гость».

## Меню, КБЖУ и фото

`POST /restaurants/{restaurantId}/menu`, `PATCH`/`DELETE /restaurants/{restaurantId}/menu/{itemId}` редактируют общий каталог. Эти изменения не меняют меню уже созданного банкета. Чтобы изменить только конкретный банкет, используйте `POST /events/{eventId}/menu`, `PATCH`/`DELETE /events/{eventId}/menu/{itemId}`. Категория «Напитки» работает как любая другая; при первом запуске есть пример нескольких безалкогольных напитков.

Новая позиция содержит название, описание, категорию, цену в копейках, вес/объём, аллергены, доступность и КБЖУ **на одну порцию**:

```json
{
  "name":"Яблочный сок",
  "description":"Свежевыжатый, без сахара",
  "category":"Напитки",
  "price":29000,
  "weight":"250 мл",
  "allergens":[],
  "labels":["Мало калорий"],
  "vegetarian":true,
  "available":true,
  "nutrition":{"kcal":110,"protein":0,"fat":0,"carbs":26.5},
  "photoUrl":""
}
```

Калории — целое число; белки, жиры и углеводы — граммы с точностью до 0,1. Примеры КБЖУ в стартовом меню ориентировочные и требуют проверки рестораном. Позиции старых пользовательских каталогов могут ещё не иметь КБЖУ, пока их не обновят. Если блюдо уже выбрано, его цена, название и доступность в меню банкета заблокированы; описание, КБЖУ и фото редактируются.

`labels` — необязательный список без повторов: `Халяль`, `Много белка`, `Мало калорий`. Его можно редактировать как в каталоге, так и в меню конкретного банкета. Старые позиции без поля возвращаются с `labels: []`. Пометку «Халяль» добавляйте только после подтверждения рестораном; сервис её не вычисляет по составу автоматически.

Фото загрузите бинарным запросом `POST /media` с `Content-Type: image/jpeg`, `image/png` или `image/webp`, размером до 3 МиБ. Ответ `{"photoUrl":"/api/media/<имя>"}` используйте в JSON позиции. Для production абсолютный адрес фото образуется как `https://mail.lonelycraft.ru/banquet` + `photoUrl`. `GET /media/{fileName}` открыт для показа карточек. Файлы и SQLite хранятся в постоянном Docker-томе.

## Уведомления

`PUT /me/notifications` с `{"enabled":true}` включает уведомления для текущего пользователя, `false` выключает. По умолчанию они выключены. Также нужен начатый личный диалог с ботом: `GET /me` показывает его в `botConnected`, интерфейс предлагает открыть чат; после `bot_stopped` отправка останавливается. Очередь отправляет организатору новости о входе и выборе гостя, гостю — напоминание до дедлайна и результат утверждения, ресторану — сообщение об утверждённом заказе. При изменении параметров банкета присоединившиеся гости получают обновление. Напоминание отменяется после сохранения выбора. Доставка через MAX может задерживаться; отправка внешнему пользователю возможна только если он включил уведомления и не остановил бота.

Административные операции из этого документа доступны и через Mini App, и через HTTP API. Сервер всегда проверяет роль, владение, телефон гостя, статус и актуальность заказа независимо от интерфейса.
