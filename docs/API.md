# API сервиса «За столом»

Базовый адрес API: **`https://mail.lonelycraft.ru/banquet/api/v1`** — все пути ниже указаны относительно него (например, `GET /me` → `https://mail.lonelycraft.ru/banquet/api/v1/me`). Машиночитаемая схема: [openapi.yaml](../openapi.yaml), она же опубликована по адресу `https://mail.lonelycraft.ru/banquet/openapi.yaml`; интерактивная документация Swagger UI — `https://mail.lonelycraft.ru/banquet/swagger/`. Как получить тестовые учётные записи и пройти обязательные проверки, описано в [TESTING.md](TESTING.md) и [DATA-API.yaml](../DATA-API.yaml). Запросы с JSON отправляйте с `Content-Type: application/json`; все цены и суммы передаются **в целых копейках**, даты — ISO 8601 с часовым поясом. Ошибки имеют вид `{"error":"..."}`. Идентификаторы берите из ответов API.

## Вход и роли

В Mini App передайте исходную строку `window.WebApp.initData` в `POST /auth/max`:

```json
{"initData":"<строка MAX Bridge>"}
```

Ответ содержит `token` сервиса и `user`. Во всех защищённых запросах используйте `Authorization: Bearer <token сервиса>`. **Токен бота MAX для этого не подходит и никогда не отправляется из браузера.** Для локальной проверки можно войти через `POST /auth/demo` с `{"role":"organizer"}`; демо-данные изолированы и не имеют доступа к реальным банкетам.

Права разделены по уровню. `GET /me` возвращает `access: [{restaurantId,restaurantName,role}]` только для администраторов ресторанов, `superAdmin` и сводную роль `role`. Любой вошедший через MAX может создать банкет в доступном ресторане и автоматически становится его организатором. Его полномочия относятся только к этому банкету: параметры, гости, меню, рассадка, общий стол, утверждение и экспорт. Назначенный организатор имеет те же права. Вкладки «Рестораны» и «Кухня» доступны только администраторам ресторана или сервиса.

`GET /users?q=...` доступен администратору ресторана и организатору банкета; он возвращает только пользователей с правами в доступных ресторанах либо добавленных в доступные банкеты, до 200 записей. Посторонние пользователи и их телефоны не показываются. Организатор назначается на конкретный банкет через `PUT /events/{eventId}/organizers/{identity}` с `{"enabled":true}`; снять роль можно через `DELETE` или `PUT` с `enabled:false`. `GET /events/{eventId}/organizers` возвращает назначенных лиц и создателя. Назначать может текущий организатор, администратор этого ресторана или администратор сервиса. Создателя снять нельзя. `identity` — ID из списка, `max:<MAX ID>` или `phone:<номер>` (URL-кодируйте параметр пути). Назначение по телефону вступит в силу, когда человек подтвердит этот номер через MAX. Администраторов ресторана назначает администратор сервиса через `PUT /restaurants/{id}/members/{identity}` с `{"role":"admin"}`; роль `organizer` для ресторана больше не используется. Любой пользователь с ролью также может быть гостем конкретного банкета.

## Создание банкета и список гостей

Глобальный администратор может выдать такую же роль другому MAX-пользователю через `PUT /admins/{userId}` с `{"enabled":true}` или снять её с `{"enabled":false}`. Вместо `userId` принимается числовой MAX ID; пользователь может ещё не открывать приложение. Назначенный администратор получает доступ ко всем ресторанам. Снять собственную роль или роль, закреплённую в `RESTAURANT_ADMIN_IDS`, нельзя. Роли можно назначать в интерфейсе «Доступы».

`GET /restaurants` возвращает **все рестораны любому вошедшему пользователю** с `menu`, `halls`, `packageDishes`, `packages` и личным флагом `favorite`. Гость и организатор могут смотреть каталог и условия залов, но редактировать ресторан может только его администратор. Отсутствие роли отмечается `access:null`; право просмотра не считается ролью в ресторане. `PUT /restaurants/{restaurantId}/favorite` добавляет ресторан в избранное текущего пользователя, `DELETE` убирает. В «Петръ» остаётся меню из предоставленных фотографий, тестовые позиции вынесены в «Temp». Каждая позиция обоих стартовых каталогов имеет иллюстративное фото; сторонние снимки «Петръ» имеют [атрибуцию](../public/petr-photos/credits.html). КБЖУ в исходном и пакетном меню являются тестовыми данными.

Администратор ресторана управляет залами через `POST /restaurants/{restaurantId}/halls`, `PATCH`/`DELETE /restaurants/{restaurantId}/halls/{hallId}`. Зал содержит `name`, `capacity`, `windows` и `seatingConfig`. В `seatingConfig.type="fixed"` администратор сохраняет конкретную `fixedLayout:{tables:[...]}` с координатами столов и количеством стульев; новые банкеты получают её копию. Организатор выбирает `seating.mode`: `choice` — гости выбирают стулья, `fixed` — организатор назначает места, `off` — без рассадки. Во всех трёх случаях столы и стулья остаются на местах ресторана. Число мест в готовой схеме должно быть от 1 до вместимости зала. В `type="flexible"` ресторан задаёт `tablePresets:[{shape:"round"|"rect",seats:8},...]`; организатор может двигать, поворачивать, добавлять и убирать столы только этих форм и размеров в пределах вместимости. Для новых залов режим и набор задаются в редакторе. Старые банкеты сохраняют свои схемы при изменении настроек зала. Поля `allowedSeating`, `allowFreeSeating` и `defaultSeatingTemplate` остаются в ответах для совместимости; `seatingConfig` является основным источником правил. `fixed` в `seating.mode` означает, что места назначает организатор, и не равен фиксированной схеме зала.

Окна задаются массивом `{weekday:0..6,start:"09:00",end:"23:00"}` по московскому времени; воскресенье — 0. Интервалы одного дня не могут пересекаться. Конец интервала может быть `24:00`; для круглосуточной работы задайте семь окон `00:00–24:00` — по одному на каждый день недели. Тогда банкеты могут переходить через полночь. `23:59` не включает последнюю минуту суток. `GET /restaurants/{restaurantId}/availability?date=YYYY-MM-DD&hallId=...` возвращает окна и занятые интервалы. `GET /restaurants/{restaurantId}/availability/month?month=YYYY-MM&hallId=...&durationHours=4` возвращает свободные моменты начала с шагом 30 минут для мини-календаря; при редактировании своей брони передайте `excludeEventId`. Дата начала банкета в интерфейсе выбирается только в календаре, после выбора зала и длительности. Продолжительность — целое `durationHours` от 1 до 12; интервал должен помещаться в часы работы и не пересекаться с другой бронью того же зала. Сервер повторно проверяет бронь при сохранении и возвращает `409` только с занятым интервалом, без данных другого мероприятия.

Блюда только для пакетов редактируются через `POST /restaurants/{restaurantId}/package-dishes`, `PATCH`/`DELETE /restaurants/{restaurantId}/package-dishes/{dishId}`. Тело: `name`, `category`, `description`, `weight`, `photoUrl`, `nutrition:{kcal,protein,fat,carbs}`, `allergens`, `labels`, `vegetarian`, `available`. Ответ содержит `packageOnly:true`; такие блюда не входят в обычное меню. Пакет создаётся через `POST /restaurants/{restaurantId}/packages` (редактирование `PATCH`, удаление `DELETE`): `{"name":"Ужин","price":450000,"items":[{"dishId":"package_dish_...","grams":250,"choiceGroup":""}]}`. Для нескольких вариантов горячего укажите одинаковую непустую `choiceGroup` для этих позиций; при создании банкета выберите один вариант по `dishId`. Состав и данные блюд копируются в банкет и не меняются от последующих правок каталога.

1. `GET /restaurants` — получить все рестораны и их текущий каталог; просмотр доступен гостю и организатору, изменение каталога — только администратору соответствующего ресторана.
2. `POST /events` — создать банкет. Тело: `restaurantId`, `hallId`, `title`, `date`, `durationHours`, `deadline`, `expectedGuests`, необязательные `foodBudget`, `drinkBudget` и `photoUrl`. Бюджеты одного гостя на еду и на напитки задаются в копейках (0 — без ограничения). `photoUrl` берётся из `POST /media`. Сервер создаёт снимок доступных блюд. В зале с готовой схемой столы копируются в банкет, а `seating:{mode}` выбирает `choice`, `fixed` или `off`; без указания режима действует `choice`. Передать свою схему столов нельзя. В гибком зале организатор затем расставляет разрешённые столы в разделе «Рассадка».
   Для фиксированного заказа добавьте `"selectionMode":"package"`, `"packageId":"package_..."` и, если пакет включает альтернативы горячего, `"packageChoice":"package_dish_..."`. По умолчанию действует `"selectionMode":"individual"`. В пакетном режиме гость видит состав, но `canSelect=false`; итог равен цене пакета × числу гостей плюс общий стол. Утвердить пакет можно без гостевых заявок.
3. `PATCH /events/{eventId}` — изменить название, дату, зал, длительность, срок выбора, число гостей, бюджеты или фото. Пустая строка `photoUrl` убирает фото. Передайте `expectedRevision` из последнего `GET /events/{eventId}`. При устаревшей ревизии получите `409` и должны перечитать данные.
   `DELETE /events/{eventId}` удаляет банкет со всеми его приглашениями, заказами и рассадкой. До утверждения доступно организатору этого банкета и администратору его ресторана; после утверждения — только администратору ресторана. Ответ `GET /events/{eventId}` содержит `event.canDelete` для интерфейса. Операция необратима.
4. `POST /events/{eventId}/guests` с `{"name":"Анна","phone":"+7 999 123-45-67"}` — добавить гостя. `PATCH` и `DELETE /events/{eventId}/guests/{guestId}` — изменить или удалить запись. Телефон нельзя поменять после привязки к MAX; гостя с сохранённым выбором удалить нельзя.
5. `GET /events/{eventId}` — владельцу и ресторану вернёт `invitedGuests`, `guests`, `summary` и ссылки приглашения. Телефоны не включены в публичный просмотр по ссылке и в ответ чужому гостю.

Число гостей — ориентир для интерфейса; при добавлении записи список может увеличить `expectedGuests`. Все изменения разрешены до утверждения. После утверждения состав заказа фиксируется. По персональной ссылке может войти и человек, которого организатор не добавил заранее: после подтверждения номера через MAX сервис создаёт его собственную запись. Ссылка не даёт права выбрать чужие блюда.

## Подтверждение гостя и заказ

Гость входит через MAX и разрешает `window.WebApp.requestContact()` в нативном окне. Результат `{phone, authDate, hash}` передаётся в `PUT /me/phone`. Сервер проверяет подпись MAX с токеном бота и связывает номер с проверенным MAX ID из сессии. Подменить `userId` параметром запроса нельзя. При открытии **общей кнопкой бота** Mini App автоматически вызывает `POST /me/claim-invitations` для уже подтверждённого номера и показывает новые банкеты; отдельная кнопка поиска не требуется. При персональной ссылке Mini App запрашивает номер, если он ещё не подтверждён, затем вызывает `POST /invites/{code}/join`. Один номер не может быть привязан к двум аккаунтам; одна запись банкета не может принадлежать двум гостям.

`GET /events/{eventId}` возвращает меню, `canSelect` и собственный `selection`. `PUT /events/{eventId}/selection` полностью заменяет выбор текущего пользователя:

```json
{
  "items": [{"menuItemId":"dish_...","quantity":2}],
  "notes":"Без орехов"
}
```

Создатель банкета тоже может выбрать блюда (и место при режиме `choice`) для себя без записи в списке гостей; его выбор входит в общий заказ. Цена и сумма вычисляются сервером из меню банкета. Если блюда дороже `event.foodBudget` или напитки (категория «Напитки») дороже `event.drinkBudget`, сервер вернёт `409`; неиспользованный бюджет на еду не переносится на напитки и наоборот. Позиции с `forGuests: false` и позиции общего стола выбрать нельзя (`400`). Гость не может передать ID другого пользователя. После дедлайна или утверждения изменения блокируются. `POST /events/{eventId}/approve` с `{"expectedRevision":12}` утверждает текущую версию. Для кухни доступны `GET /events/{eventId}/export.csv` и одноразовая ссылка `POST /events/{eventId}/export-link`.

## Меню банкета и общий стол

Меню банкета — снимок каталога. При создании туда попадают все доступные блюда; поэтому отсутствие новых позиций для импорта не означает, что выбор каталога недоступен. `PUT /events/{eventId}/menu/catalog` с `{"itemIds":["dish_..."]}` атомарно сохраняет выбранный набор блюд из текущего каталога: отсутствующие добавляет, снятые удаляет. Собственные позиции банкета и блюда, исчезнувшие из каталога после создания банкета, сохраняются отдельно. Убрать блюдо, которое уже заказали гости или поставили на общий стол, нельзя; весь запрос в таком случае отклоняется без частичных изменений. `POST /events/{eventId}/menu/import` по-прежнему добавляет только отсутствующие позиции. У каждой позиции есть флаг `forGuests`: `PATCH /events/{eventId}/menu/{itemId}` с `{"forGuests":false}` скрывает её от гостей (гостям такие позиции не отдаются). Позицию, которую уже выбрал гость, скрыть нельзя.

Организатор банкета может выбрать позиции из каталога, переключить их доступность гостям, указать количество для общего стола и убрать незаказанную позицию из меню банкета. Создавать собственное блюдо через `POST /events/{eventId}/menu` и редактировать название, описание, цену, фото или КБЖУ через `PATCH` может только администратор ресторана или администратор приложения. Попытка организатора передать любые поля кроме единственного `forGuests` возвращает `403`.

`PUT /events/{eventId}/shared` задаёт общий стол целиком:

```json
{"items": [{"menuItemId":"dish_...","quantity":3}]}
```

Позиции общего стола входят в `event.total` и сводку кухни, но не в бюджет гостя. Гости видят их в `detail.shared` и не могут заказать сами. Позицию, которую уже заказал гость, на общий стол перенести нельзя.

## Внутренняя валюта гостя

API всегда работает в копейках; пересчёт делает интерфейс гостя (`shared/currency.mjs`). Организатор задаёт в рублях два независимых лимита на одного гостя: на еду и напитки. Гостю еда показывается в кусочках пирога 🥧 (1 = 10 ₽), позиции категории «Напитки» — в бутылочках 🍾 (1 = 100 ₽). Например, 2 500 ₽ на еду дают 250 🥧, а 600 ₽ на напитки — 6 🍾. При выборе порции её стоимость вычитается только из соответствующего остатка; переносить неиспользованный лимит между категориями нельзя. Значение бюджета `0` означает отсутствие ограничения в этой категории. Это только единицы отображения, а не платежи: итоговая стоимость заказа считается в рублях. Дробные значения единиц допустимы и отображаются до двух знаков.

## Администратор и кухня

`GET /kitchen` возвращает банкеты ресторанов, где пользователь — администратор, с датой не раньше вчерашнего дня: `event` (с `ownerName`), порции `summary` с учётом общего стола, `shared`, `seating` и гостей с выбором, пожеланиями и местом. Владелец и администратор также получают `event.ownerName`, `event.sharedTotal` и плановый `event.budget = (foodBudget + drinkBudget) × expectedGuests`. `GET /kitchen/export?format=xlsx|csv&eventIds=event_...,event_...` выгружает выбранные мероприятия; для загрузки внутри MAX используйте `POST /kitchen/export-link` с `{"format":"xlsx","eventIds":["event_...","event_..."]}` и `WebApp.downloadFile`. Передавать можно от 1 до 100 доступных ID. Без `eventIds` API выгружает все доступные мероприятия. Excel содержит листы «Порции», «Гости», «Рассадка» и «Пакеты»; CSV содержит те же блоки.

## Рассадка

`GET /events/{eventId}` возвращает `seating` со схемой, занятыми местами `occupied` и собственным местом `mySeat`. Управляющие также получают `people`, `canCustomize`, `allowedModes`, `layoutPolicy`, `tablePresets` и `hallCapacity`. При готовой схеме `canCustomize=false`: никто не передвигает столы в банкете, но управляющий может менять `mode` через `PUT /events/{eventId}/seating` без поля `layout`. При `off` назначенные места освобождаются; назначение и выбор мест запрещены до повторного включения рассадки. При гибкой схеме организатор расставляет столы из `tablePresets`; сервер отклоняет другие размеры и превышение вместимости.

`PUT /events/{eventId}/seating` включает рассадку и сохраняет схему целиком:

```json
{
  "mode": "choice",
  "layout": {"tables": [
    {"id":"t1","shape":"round","label":"1","x":60,"y":60,"w":120,"h":120,"rotation":0,"seats":8},
    {"id":"t2","shape":"rect","label":"Президиум","x":300,"y":60,"w":300,"h":70,"rotation":0,"seats":5,"sides":["top"]}
  ]}
}
```

Режимы: `off` — без рассадки, `choice` — гости выбирают места сами, `fixed` — места назначает организатор. Стулья не передаются: их номера и координаты вычисляются из стола, id места имеет вид `<tableId>-<n>`, нумерация идёт по часовой стрелке. Готовые шаблоны в старых банкетах сохраняются, а новые схемы проверяются по набору столов ресторана. Сохранить схему, в которой пропадает уже занятое место, нельзя: сервер вернёт `409` и перечислит такие места.

Гость выбирает место через `PUT /events/{eventId}/seat` с `{"seatId":"t1-3"}`, а `{"seatId":null}` освобождает его. Если место уже занято, сервер вернёт `409`. Организатор назначает места через `PUT /events/{eventId}/seating/assignments` с `{"guest":"invite:...","seatId":"t2-1"}`; `guest` берётся из `seating.people[].key`. Если место занято, гости меняются местами. Любой участник банкета видит в `seating.names` имена гостей на занятых местах (`{"t1-2":"Мария"}`); телефоны и полный список гостей получают организаторы банкета и администраторы ресторана (`seating.people`). `POST /events/{eventId}/seating/auto` рассаживает всех гостей без места: сначала за столы, где уже кто-то сидит, затем за пустые. То же происходит автоматически при утверждении заказа. После утверждения рассадка фиксируется, а CSV получает колонку «Место» и отдельный блок «Стол / Место / Гость».

## Меню, КБЖУ и фото

`POST /restaurants/{restaurantId}/menu`, `PATCH`/`DELETE /restaurants/{restaurantId}/menu/{itemId}` редактируют общий каталог. Эти изменения не меняют меню уже созданного банкета. Чтобы изменить только конкретный банкет, используйте `POST /events/{eventId}/menu`, `PATCH`/`DELETE /events/{eventId}/menu/{itemId}`. Категория «Напитки» работает как любая другая; при первом запуске есть пример нескольких безалкогольных напитков.

Новая позиция содержит название, описание, категорию, цену в копейках, вес/объём, аллергены, доступность и КБЖУ **на одну порцию**:

```json
{
  "name":"Яблочный сок",
  "description":"Свежевыжатый, без сахара",
  "category":"Напитки",
  "price":29000,
  "weight":"250 мл",
  "allergens":[],
  "labels":["Мало калорий"],
  "vegetarian":true,
  "available":true,
  "nutrition":{"kcal":110,"protein":0,"fat":0,"carbs":26.5},
  "photoUrl":""
}
```

Калории — целое число; белки, жиры и углеводы — граммы с точностью до 0,1. Примеры КБЖУ в стартовом меню ориентировочные и требуют проверки рестораном. Позиции старых пользовательских каталогов могут ещё не иметь КБЖУ, пока их не обновят. Если блюдо уже выбрано, его цена, название и доступность в меню банкета заблокированы; описание, КБЖУ и фото редактируются.

`labels` — необязательный список без повторов: `Халяль`, `Много белка`, `Мало калорий`. Его можно редактировать как в каталоге, так и в меню конкретного банкета. Старые позиции без поля возвращаются с `labels: []`. Пометку «Халяль» добавляйте только после подтверждения рестораном; сервис её не вычисляет по составу автоматически.

Фото загрузите бинарным запросом `POST /media` с `Content-Type: image/jpeg`, `image/png` или `image/webp`, размером до 10 МиБ. Ответ `{"photoUrl":"/api/media/<имя>"}` используйте в JSON позиции. Для production абсолютный адрес фото образуется как `https://mail.lonelycraft.ru/banquet` + `photoUrl`. `GET /media/{fileName}` открыт для показа карточек. Файлы и SQLite хранятся в постоянном Docker-томе.

## Уведомления

`PUT /me/notifications` с `{"enabled":true}` включает уведомления для текущего пользователя, `false` выключает. По умолчанию они выключены. Тем же запросом можно указать одну или несколько категорий: `{"categories":{"guestJoined":false,"guestSelection":true,"eventChanges":true,"reminders":true,"orderApproved":true,"kitchenOrders":true}}`. Неуказанные категории не меняются; изначально все категории включены, пока выключено общее разрешение. `GET /me` возвращает `notificationPreferences` и `notificationsEnabled`. Отключённые категории не ставятся в очередь, а ожидающие сообщения этой категории отменяются без последующей отправки при повторном включении. Также нужен начатый личный диалог с ботом: `GET /me` показывает его в `botConnected`, интерфейс предлагает открыть чат; после `bot_stopped` отправка останавливается. `guestJoined` и `guestSelection` — новости для организатора, `eventChanges` — изменения банкета для гостей, `reminders` — напоминание до дедлайна, `orderApproved` — итог для гостей, `kitchenOrders` — утверждённый заказ для ресторана. Напоминание отменяется после сохранения выбора. Доставка через MAX может задерживаться; отправка внешнему пользователю возможна только если он включил уведомления и не остановил бота.

Административные операции из этого документа доступны и через Mini App, и через HTTP API. Сервер всегда проверяет роль, владение, телефон гостя, статус и актуальность заказа независимо от интерфейса.
