# API сервиса «За столом»

Полная машиночитаемая схема находится в [openapi.yaml](../openapi.yaml). Production base URL: `https://mail.lonelycraft.ru/banquet`. Запросы с JSON отправляйте с `Content-Type: application/json`; все цены и суммы передаются **в целых копейках**, даты — ISO 8601 с часовым поясом. Ошибки имеют вид `{"error":"..."}`. Идентификаторы берите из ответов API.

## Вход и роли

В Mini App передайте исходную строку `window.WebApp.initData` в `POST /api/auth/max`:

```json
{"initData":"<строка MAX Bridge>"}
```

Ответ содержит `token` сервиса и `user`. Во всех защищённых запросах используйте `Authorization: Bearer <token сервиса>`. **Токен бота MAX для этого не подходит и никогда не отправляется из браузера.** Для локальной проверки можно войти через `POST /api/auth/demo` с `{"role":"organizer"}`; демо-данные изолированы и не имеют доступа к реальным банкетам.

Права разделены по уровню. `GET /api/me` возвращает `access: [{restaurantId,restaurantName,role}]` только для администраторов ресторанов, `superAdmin` и сводную роль `role`. Любой вошедший через MAX может создать банкет в доступном ресторане и автоматически становится его организатором. Его полномочия относятся только к этому банкету: параметры, гости, меню, рассадка, общий стол, утверждение и экспорт. Назначенный организатор имеет те же права. Вкладки «Рестораны» и «Кухня» доступны только администраторам ресторана или сервиса.

`GET /api/users?q=...` доступен администратору ресторана и организатору банкета; он возвращает только пользователей с правами в доступных ресторанах либо добавленных в доступные банкеты, до 200 записей. Посторонние пользователи и их телефоны не показываются. Организатор назначается на конкретный банкет через `PUT /api/events/{eventId}/organizers/{identity}` с `{"enabled":true}`; снять роль можно через `DELETE` или `PUT` с `enabled:false`. `GET /api/events/{eventId}/organizers` возвращает назначенных лиц и создателя. Назначать может текущий организатор, администратор этого ресторана или администратор сервиса. Создателя снять нельзя. `identity` — ID из списка, `max:<MAX ID>` или `phone:<номер>` (URL-кодируйте параметр пути). Назначение по телефону вступит в силу, когда человек подтвердит этот номер через MAX. Администраторов ресторана назначает администратор сервиса через `PUT /api/restaurants/{id}/members/{identity}` с `{"role":"admin"}`; роль `organizer` для ресторана больше не используется. Любой пользователь с ролью также может быть гостем конкретного банкета.

## Создание банкета и список гостей

Глобальный администратор может выдать такую же роль другому MAX-пользователю через `PUT /api/admins/{userId}` с `{"enabled":true}` или снять её с `{"enabled":false}`. Вместо `userId` принимается числовой MAX ID; пользователь может ещё не открывать приложение. Назначенный администратор получает доступ ко всем ресторанам. Снять собственную роль или роль, закреплённую в `RESTAURANT_ADMIN_IDS`, нельзя. Роли можно назначать в интерфейсе «Доступы».

`GET /api/restaurants` возвращает **все рестораны любому вошедшему пользователю** с `menu`, `halls`, `packageDishes`, `packages` и личным флагом `favorite`. Гость и организатор могут смотреть каталог и условия залов, но редактировать ресторан может только его администратор. Отсутствие роли отмечается `access:null`; право просмотра не считается ролью в ресторане. `PUT /api/restaurants/{restaurantId}/favorite` добавляет ресторан в избранное текущего пользователя, `DELETE` убирает. В «Петръ» остаётся меню из предоставленных фотографий, тестовые позиции вынесены в «Temp». Каждая позиция обоих стартовых каталогов имеет иллюстративное фото; сторонние снимки «Петръ» имеют [атрибуцию](../public/petr-photos/credits.html). КБЖУ в исходном и пакетном меню являются тестовыми данными.

Администратор ресторана управляет залами через `POST /api/restaurants/{restaurantId}/halls`, `PATCH`/`DELETE /api/restaurants/{restaurantId}/halls/{hallId}`. Зал содержит `name`, `capacity`, `allowedSeating` (`choice`, `fixed`), `defaultSeatingTemplate` (одна из схем `rounds`, `u`, `presidium`, `t`, `long`) и `windows`: массив `{weekday:0..6,start:"09:00",end:"23:00"}` по московскому времени; воскресенье — 0. В ответе также есть `allowFreeSeating`, равный наличию `choice` в `allowedSeating`. Новые банкеты по умолчанию используют стандартную схему зала и фиксированную рассадку: места назначает организатор. Если администратор уберёт `choice`, организатор не сможет менять схему или включать свободный выбор мест гостями, но сможет назначать места на стандартной схеме. Если `choice` разрешён, организатор может выбрать другую схему и режим. Изменение настройки зала не меняет схемы уже созданных банкетов. Интервалы одного дня не могут пересекаться. Конец интервала может быть `24:00`; для круглосуточной работы задайте семь окон `00:00–24:00` — по одному на каждый день недели. Тогда банкеты могут переходить через полночь. `23:59` не включает последнюю минуту суток. `GET /api/restaurants/{restaurantId}/availability?date=YYYY-MM-DD&hallId=...` возвращает окна и занятые интервалы залов, включая начавшиеся накануне ночные банкеты. Чужие банкеты не раскрывают ID или название. `GET /api/restaurants/{restaurantId}/availability/month?month=YYYY-MM&hallId=...&durationHours=4` возвращает дни и свободные моменты начала с шагом 30 минут по Москве для мини-календаря. При редактировании собственного банкета можно передать `excludeEventId`, чтобы текущая бронь не блокировала свои слоты; параметр доступен только управляющему этим банкетом. Продолжительность банкета задаётся целым `durationHours` от 1 до 12; весь интервал должен помещаться в часы работы. Брони одного зала не могут пересекаться, разные залы могут быть заняты одновременно. Сервер проверяет бронь атомарно при создании и изменении; при конфликте возвращает `409` только с занятым интервалом, без данных другого мероприятия. Вместимость ограничивает число гостей, в том числе при добавлении приглашений.

Блюда только для пакетов редактируются через `POST /api/restaurants/{restaurantId}/package-dishes`, `PATCH`/`DELETE /api/restaurants/{restaurantId}/package-dishes/{dishId}`. Тело: `name`, `category`, `description`, `weight`, `photoUrl`, `nutrition:{kcal,protein,fat,carbs}`, `allergens`, `labels`, `vegetarian`, `available`. Ответ содержит `packageOnly:true`; такие блюда не входят в обычное меню. Пакет создаётся через `POST /api/restaurants/{restaurantId}/packages` (редактирование `PATCH`, удаление `DELETE`): `{"name":"Ужин","price":450000,"items":[{"dishId":"package_dish_...","grams":250,"choiceGroup":""}]}`. Для нескольких вариантов горячего укажите одинаковую непустую `choiceGroup` для этих позиций; при создании банкета выберите один вариант по `dishId`. Состав и данные блюд копируются в банкет и не меняются от последующих правок каталога.

1. `GET /api/restaurants` — получить все рестораны и их текущий каталог; просмотр доступен гостю и организатору, изменение каталога — только администратору соответствующего ресторана.
2. `POST /api/events` — создать банкет. Тело: `restaurantId`, `hallId`, `title`, `date`, `durationHours`, `deadline`, `expectedGuests`, необязательные `foodBudget`, `drinkBudget` и `photoUrl`. Бюджеты одного гостя на еду и на напитки задаются в копейках (0 — без ограничения). `photoUrl` берётся из `POST /api/media`. Сервер создаёт снимок доступных блюд. Необязательный объект `seating:{mode,template}` сохраняется атомарно при создании; без него применяется фиксированная стандартная рассадка выбранного зала. Организатор может переопределить её, только если зал разрешает свободную рассадку.
   Для фиксированного заказа добавьте `"selectionMode":"package"`, `"packageId":"package_..."` и, если пакет включает альтернативы горячего, `"packageChoice":"package_dish_..."`. По умолчанию действует `"selectionMode":"individual"`. В пакетном режиме гость видит состав, но `canSelect=false`; итог равен цене пакета × числу гостей плюс общий стол. Утвердить пакет можно без гостевых заявок.
3. `PATCH /api/events/{eventId}` — изменить название, дату, зал, длительность, срок выбора, число гостей, бюджеты или фото. Пустая строка `photoUrl` убирает фото. Передайте `expectedRevision` из последнего `GET /api/events/{eventId}`. При устаревшей ревизии получите `409` и должны перечитать данные.
   `DELETE /api/events/{eventId}` удаляет банкет со всеми его приглашениями, заказами и рассадкой. До утверждения доступно организатору этого банкета и администратору его ресторана; после утверждения — только администратору ресторана. Ответ `GET /api/events/{eventId}` содержит `event.canDelete` для интерфейса. Операция необратима.
4. `POST /api/events/{eventId}/guests` с `{"name":"Анна","phone":"+7 999 123-45-67"}` — добавить гостя. `PATCH` и `DELETE /api/events/{eventId}/guests/{guestId}` — изменить или удалить запись. Телефон нельзя поменять после привязки к MAX; гостя с сохранённым выбором удалить нельзя.
5. `GET /api/events/{eventId}` — владельцу и ресторану вернёт `invitedGuests`, `guests`, `summary` и ссылки приглашения. Телефоны не включены в публичный просмотр по ссылке и в ответ чужому гостю.

Число гостей — ориентир для интерфейса; при добавлении записи список может увеличить `expectedGuests`. Все изменения разрешены до утверждения. После утверждения состав заказа фиксируется. По персональной ссылке может войти и человек, которого организатор не добавил заранее: после подтверждения номера через MAX сервис создаёт его собственную запись. Ссылка не даёт права выбрать чужие блюда.

## Подтверждение гостя и заказ

Гость входит через MAX и разрешает `window.WebApp.requestContact()` в нативном окне. Результат `{phone, authDate, hash}` передаётся в `PUT /api/me/phone`. Сервер проверяет подпись MAX с токеном бота и связывает номер с проверенным MAX ID из сессии. Подменить `userId` параметром запроса нельзя. При открытии **общей кнопкой бота** Mini App автоматически вызывает `POST /api/me/claim-invitations` для уже подтверждённого номера и показывает новые банкеты; отдельная кнопка поиска не требуется. При персональной ссылке Mini App запрашивает номер, если он ещё не подтверждён, затем вызывает `POST /api/invites/{code}/join`. Один номер не может быть привязан к двум аккаунтам; одна запись банкета не может принадлежать двум гостям.

`GET /api/events/{eventId}` возвращает меню, `canSelect` и собственный `selection`. `PUT /api/events/{eventId}/selection` полностью заменяет выбор текущего пользователя:

```json
{
  "items": [{"menuItemId":"dish_...","quantity":2}],
  "notes":"Без орехов"
}
```

Создатель банкета тоже может выбрать блюда (и место при режиме `choice`) для себя без записи в списке гостей; его выбор входит в общий заказ. Цена и сумма вычисляются сервером из меню банкета. Если блюда дороже `event.foodBudget` или напитки (категория «Напитки») дороже `event.drinkBudget`, сервер вернёт `409`; неиспользованный бюджет на еду не переносится на напитки и наоборот. Позиции с `forGuests: false` и позиции общего стола выбрать нельзя (`400`). Гость не может передать ID другого пользователя. После дедлайна или утверждения изменения блокируются. `POST /api/events/{eventId}/approve` с `{"expectedRevision":12}` утверждает текущую версию. Для кухни доступны `GET /api/events/{eventId}/export.csv` и одноразовая ссылка `POST /api/events/{eventId}/export-link`.

## Меню банкета и общий стол

Меню банкета — снимок каталога. При создании туда попадают все доступные блюда; поэтому отсутствие новых позиций для импорта не означает, что выбор каталога недоступен. `PUT /api/events/{eventId}/menu/catalog` с `{"itemIds":["dish_..."]}` атомарно сохраняет выбранный набор блюд из текущего каталога: отсутствующие добавляет, снятые удаляет. Собственные позиции банкета и блюда, исчезнувшие из каталога после создания банкета, сохраняются отдельно. Убрать блюдо, которое уже заказали гости или поставили на общий стол, нельзя; весь запрос в таком случае отклоняется без частичных изменений. `POST /api/events/{eventId}/menu/import` по-прежнему добавляет только отсутствующие позиции. У каждой позиции есть флаг `forGuests`: `PATCH /api/events/{eventId}/menu/{itemId}` с `{"forGuests":false}` скрывает её от гостей (гостям такие позиции не отдаются). Позицию, которую уже выбрал гость, скрыть нельзя.

`PUT /api/events/{eventId}/shared` задаёт общий стол целиком:

```json
{"items": [{"menuItemId":"dish_...","quantity":3}]}
```

Позиции общего стола входят в `event.total` и сводку кухни, но не в бюджет гостя. Гости видят их в `detail.shared` и не могут заказать сами. Позицию, которую уже заказал гость, на общий стол перенести нельзя.

## Внутренняя валюта гостя

API всегда работает в копейках; пересчёт делает интерфейс гостя (`shared/currency.mjs`). Это две независимые валюты: еда стоит кусочки пирога 🥧 (1 = 10 ₽), позиции категории «Напитки» — бутылочки 🍾 (1 = 100 ₽). Интерфейс показывает значения иконками, дробные значения не округляются до целых. Бюджет гостя отображается двумя шкалами: еда в кусочках, напитки в бутылочках.

## Администратор и кухня

`GET /api/kitchen` возвращает банкеты ресторанов, где пользователь — администратор, с датой не раньше вчерашнего дня: `event` (с `ownerName`), порции `summary` с учётом общего стола, `shared`, `seating` и гостей с выбором, пожеланиями и местом. Владелец и администратор также получают `event.ownerName`, `event.sharedTotal` и плановый `event.budget = (foodBudget + drinkBudget) × expectedGuests`. `GET /api/kitchen/export?format=xlsx|csv&eventIds=event_...,event_...` выгружает выбранные мероприятия; для загрузки внутри MAX используйте `POST /api/kitchen/export-link` с `{"format":"xlsx","eventIds":["event_...","event_..."]}` и `WebApp.downloadFile`. Передавать можно от 1 до 100 доступных ID. Без `eventIds` API выгружает все доступные мероприятия. Excel содержит листы «Порции», «Гости», «Рассадка» и «Пакеты»; CSV содержит те же блоки.

## Рассадка

Новый банкет по умолчанию получает стандартную рассадку зала (`fixed`), если зал поддерживает этот режим. Для залов без разрешённых вариантов остаётся `off`. `GET /api/events/{eventId}` всегда возвращает объект `seating` со схемой зала, режимом, списком занятых мест `occupied` и собственным местом `mySeat`. Организаторы и администрация ресторана дополнительно получают `people` — всех гостей с их местами — и поле `seat` у каждого гостя. `canCustomize` показывает, может ли текущий организатор менять режим и схему; `allowedModes` перечисляет разрешённые варианты.

`PUT /api/events/{eventId}/seating` включает рассадку и сохраняет схему целиком:

```json
{
  "mode": "choice",
  "layout": {"tables": [
    {"id":"t1","shape":"round","label":"1","x":60,"y":60,"w":120,"h":120,"rotation":0,"seats":8},
    {"id":"t2","shape":"rect","label":"Президиум","x":300,"y":60,"w":300,"h":70,"rotation":0,"seats":5,"sides":["top"]}
  ]}
}
```

Режимы: `off` — без рассадки, `choice` — гости выбирают места сами, `fixed` — места назначает организатор. Стулья не передаются: их номера и координаты вычисляются из стола, id места имеет вид `<tableId>-<n>`, нумерация идёт по часовой стрелке. Готовые шаблоны (круглые столы, П-образная, с президиумом, Т-образная, длинный стол) строит функция `generateLayout` из `shared/seating.mjs`. Сохранить схему, в которой пропадает уже занятое место, нельзя: сервер вернёт `409` и перечислит такие места.

Гость выбирает место через `PUT /api/events/{eventId}/seat` с `{"seatId":"t1-3"}`, а `{"seatId":null}` освобождает его. Если место уже занято, сервер вернёт `409`. Организатор назначает места через `PUT /api/events/{eventId}/seating/assignments` с `{"guest":"invite:...","seatId":"t2-1"}`; `guest` берётся из `seating.people[].key`. Если место занято, гости меняются местами. Любой участник банкета видит в `seating.names` имена гостей на занятых местах (`{"t1-2":"Мария"}`); телефоны и полный список гостей получают организаторы банкета и администраторы ресторана (`seating.people`). `POST /api/events/{eventId}/seating/auto` рассаживает всех гостей без места: сначала за столы, где уже кто-то сидит, затем за пустые. То же происходит автоматически при утверждении заказа. После утверждения рассадка фиксируется, а CSV получает колонку «Место» и отдельный блок «Стол / Место / Гость».

## Меню, КБЖУ и фото

`POST /api/restaurants/{restaurantId}/menu`, `PATCH`/`DELETE /api/restaurants/{restaurantId}/menu/{itemId}` редактируют общий каталог. Эти изменения не меняют меню уже созданного банкета. Чтобы изменить только конкретный банкет, используйте `POST /api/events/{eventId}/menu`, `PATCH`/`DELETE /api/events/{eventId}/menu/{itemId}`. Категория «Напитки» работает как любая другая; при первом запуске есть пример нескольких безалкогольных напитков.

Новая позиция содержит название, описание, категорию, цену в копейках, вес/объём, аллергены, доступность и КБЖУ **на одну порцию**:

```json
{
  "name":"Яблочный сок",
  "description":"Свежевыжатый, без сахара",
  "category":"Напитки",
  "price":29000,
  "weight":"250 мл",
  "allergens":[],
  "labels":["Мало калорий"],
  "vegetarian":true,
  "available":true,
  "nutrition":{"kcal":110,"protein":0,"fat":0,"carbs":26.5},
  "photoUrl":""
}
```

Калории — целое число; белки, жиры и углеводы — граммы с точностью до 0,1. Примеры КБЖУ в стартовом меню ориентировочные и требуют проверки рестораном. Позиции старых пользовательских каталогов могут ещё не иметь КБЖУ, пока их не обновят. Если блюдо уже выбрано, его цена, название и доступность в меню банкета заблокированы; описание, КБЖУ и фото редактируются.

`labels` — необязательный список без повторов: `Халяль`, `Много белка`, `Мало калорий`. Его можно редактировать как в каталоге, так и в меню конкретного банкета. Старые позиции без поля возвращаются с `labels: []`. Пометку «Халяль» добавляйте только после подтверждения рестораном; сервис её не вычисляет по составу автоматически.

Фото загрузите бинарным запросом `POST /api/media` с `Content-Type: image/jpeg`, `image/png` или `image/webp`, размером до 3 МиБ. Ответ `{"photoUrl":"/api/media/<имя>"}` используйте в JSON позиции. Для production абсолютный адрес фото образуется как `https://mail.lonelycraft.ru/banquet` + `photoUrl`. `GET /api/media/{fileName}` открыт для показа карточек. Файлы и SQLite хранятся в постоянном Docker-томе.

## Уведомления

`PUT /api/me/notifications` с `{"enabled":true}` включает уведомления для текущего пользователя, `false` выключает. По умолчанию они выключены. Также нужен начатый личный диалог с ботом: `GET /api/me` показывает его в `botConnected`, интерфейс предлагает открыть чат; после `bot_stopped` отправка останавливается. Очередь отправляет организатору новости о входе и выборе гостя, гостю — напоминание до дедлайна и результат утверждения, ресторану — сообщение об утверждённом заказе. При изменении параметров банкета присоединившиеся гости получают обновление. Напоминание отменяется после сохранения выбора. Доставка через MAX может задерживаться; отправка внешнему пользователю возможна только если он включил уведомления и не остановил бота.

Административные операции из этого документа доступны и через Mini App, и через HTTP API. Сервер всегда проверяет роль, владение, телефон гостя, статус и актуальность заказа независимо от интерфейса.
