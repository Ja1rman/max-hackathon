# API сервиса «За столом»

Полная машиночитаемая схема находится в [openapi.yaml](../openapi.yaml). Production base URL: `https://mail.lonelycraft.ru/banquet`. Запросы с JSON отправляйте с `Content-Type: application/json`; все цены и суммы передаются **в целых копейках**, даты — ISO 8601 с часовым поясом. Ошибки имеют вид `{"error":"..."}`. Идентификаторы берите из ответов API.

## Вход и роли

В Mini App передайте исходную строку `window.WebApp.initData` в `POST /api/auth/max`:

```json
{"initData":"<строка MAX Bridge>"}
```

Ответ содержит `token` сервиса и `user`. Во всех защищённых запросах используйте `Authorization: Bearer <token сервиса>`. **Токен бота MAX для этого не подходит и никогда не отправляется из браузера.** Для локальной проверки можно войти через `POST /api/auth/demo` с `{"role":"organizer"}`; демо-данные изолированы и не имеют доступа к реальным банкетам.

MAX ID из существующей серверной настройки `RESTAURANT_ADMIN_IDS` получает глобальную роль `admin` (администратор сервиса); название переменной сохранено для совместимости развёртывания. Остальные MAX-пользователи имеют общую роль `user` и отдельные назначения **для каждого ресторана**. `restaurant_admin` управляет каталогом и банкетами своего ресторана и может назначать ему организаторов. `organizer` создаёт банкеты выбранного ресторана и ведёт свои мероприятия. Глобальный администратор назначает администраторов ресторанов и организаторов. Любая роль может быть гостем на мероприятии; выбор блюд привязан к конкретному MAX ID и подтверждённому номеру. **Утвердить заказ может только владелец банкета.** `GET /api/me` возвращает `restaurantRoles` и `maxId` текущего пользователя.

`POST /api/restaurants` создаёт ресторан (только `admin`); `PATCH /api/restaurants/{restaurantId}` меняет название, описание и адрес (`admin` или `restaurant_admin` этого ресторана). `GET /api/restaurants/{restaurantId}/members` показывает назначенных сотрудников. `PUT /api/restaurants/{restaurantId}/members/{maxId}` с `{"role":"restaurant_admin"}` или `{"role":"organizer"}` назначает роль по числовому MAX ID; `DELETE` снимает её. Администратор ресторана может назначить или снять только `organizer` в своём ресторане. Пользователь может ещё не заходить в сервис: его права вступят в силу при входе через MAX.

## Создание банкета и список гостей

1. `GET /api/restaurants` — получить рестораны и их текущий каталог.
2. `POST /api/events` — создать банкет в ресторане, где есть право организатора или выше. Тело: `restaurantId`, `title`, `date`, `deadline`, `expectedGuests`, необязательные `budget` и `photoUrl`. Сервер создаёт снимок доступных блюд.
3. `PATCH /api/events/{eventId}` — изменить название, дату, срок выбора, число гостей, бюджет или `photoUrl`. Передайте `expectedRevision` из последнего `GET /api/events/{eventId}`. При устаревшей ревизии получите `409` и должны перечитать данные.
4. `POST /api/events/{eventId}/guests` с `{"name":"Анна","phone":"+7 999 123-45-67"}` — добавить гостя. `PATCH` и `DELETE /api/events/{eventId}/guests/{guestId}` — изменить или удалить запись. Телефон нельзя поменять после привязки к MAX; гостя с сохранённым выбором удалить нельзя.
5. `GET /api/events/{eventId}` — владельцу и ресторану вернёт `invitedGuests`, `guests`, `summary` и ссылки приглашения. Телефоны не включены в публичный просмотр по ссылке и в ответ чужому гостю.

Число гостей — ориентир для интерфейса; при добавлении записи список может увеличить `expectedGuests`. Все изменения разрешены до утверждения. После утверждения состав заказа фиксируется. По персональной ссылке может войти и человек, которого организатор **не добавил по номеру заранее**: после подтверждения номера через MAX он получит собственную запись гостя. Ссылка не позволяет выбрать блюда за других.

## Подтверждение гостя и заказ

При первом входе гость подтверждает номер в нативном окне `window.WebApp.requestContact()`. Результат `{phone, authDate, hash}` передаётся в `PUT /api/me/phone`. Сервер проверяет подпись MAX с токеном бота и связывает номер с проверенным MAX ID из сессии. Подменить `userId` параметром запроса нельзя. При открытии **общей кнопкой бота** Mini App автоматически вызывает `POST /api/me/claim-invitations` для уже подтверждённого номера и показывает все новые доступные банкеты; отдельная кнопка поиска не нужна. При открытии персональной ссылки Mini App предлагает нативное подтверждение номера, если оно ещё не было сделано, и вызывает `POST /api/invites/{code}/join`. Один номер не может быть привязан к двум аккаунтам; одна запись банкета не может принадлежать двум гостям.

`GET /api/events/{eventId}` возвращает меню, `canSelect` и собственный `selection`. `PUT /api/events/{eventId}/selection` полностью заменяет выбор текущего пользователя:

```json
{
  "items": [{"menuItemId":"dish_...","quantity":2}],
  "notes":"Без орехов"
}
```

Цена и сумма вычисляются сервером из меню банкета. Гость не может передать ID другого пользователя. После дедлайна или утверждения изменения блокируются. `POST /api/events/{eventId}/approve` с `{"expectedRevision":12}` утверждает текущую версию. Для кухни доступны `GET /api/events/{eventId}/export.csv` и одноразовая ссылка `POST /api/events/{eventId}/export-link`.

`event.guestBudget` — мягкий ориентир на гостя, целые копейки: общий бюджет делится на `expectedGuests`. Интерфейс показывает стоимость собственного выбора и остаток/превышение; превышение не блокирует сохранение. Окончательную сумму утверждает владелец.

## Меню, КБЖУ и фото

`POST /api/restaurants/{restaurantId}/menu`, `PATCH`/`DELETE /api/restaurants/{restaurantId}/menu/{itemId}` редактируют общий каталог. Эти изменения не меняют меню уже созданного банкета. Чтобы изменить только конкретный банкет, используйте `POST /api/events/{eventId}/menu`, `PATCH`/`DELETE /api/events/{eventId}/menu/{itemId}`. Категория «Напитки» работает как любая другая; при первом запуске есть пример нескольких безалкогольных напитков.

Новая позиция содержит название, описание, категорию, цену в копейках, вес/объём, аллергены, доступность и КБЖУ **на одну порцию**:

```json
{
  "name":"Яблочный сок",
  "description":"Свежевыжатый, без сахара",
  "category":"Напитки",
  "price":29000,
  "weight":"250 мл",
  "allergens":[],
  "labels":["Мало калорий"],
  "vegetarian":true,
  "available":true,
  "nutrition":{"kcal":110,"protein":0,"fat":0,"carbs":26.5},
  "photoUrl":""
}
```

Калории — целое число; белки, жиры и углеводы — граммы с точностью до 0,1. Примеры КБЖУ в стартовом меню ориентировочные и требуют проверки рестораном. Позиции старых пользовательских каталогов могут ещё не иметь КБЖУ, пока их не обновят. Если блюдо уже выбрано, его цена, название и доступность в меню банкета заблокированы; описание, КБЖУ и фото редактируются.

`labels` — необязательный список без повторов: `Халяль`, `Много белка`, `Мало калорий`. Его можно редактировать как в каталоге, так и в меню конкретного банкета. Старые позиции без поля возвращаются с `labels: []`. Пометку «Халяль» добавляйте только после подтверждения рестораном; сервис её не вычисляет по составу автоматически.

Фото загрузите бинарным запросом `POST /api/media` с `Content-Type: image/jpeg`, `image/png` или `image/webp`, размером до 3 МиБ. Ответ `{"photoUrl":"/api/media/<имя>"}` используйте в JSON позиции. Для production абсолютный адрес фото образуется как `https://mail.lonelycraft.ru/banquet` + `photoUrl`. `GET /api/media/{fileName}` открыт для показа карточек. Файлы и SQLite хранятся в постоянном Docker-томе.

Тот же `photoUrl` можно передать при создании или изменении мероприятия; пустая строка в `PATCH /api/events/{eventId}` снимает фото. Фото показывается в карточке и на странице банкета.

## Уведомления

`PUT /api/me/notifications` с `{"enabled":true}` включает уведомления для текущего пользователя, `false` выключает. По умолчанию они выключены. Также нужен начатый личный диалог с ботом; после `bot_stopped` отправка останавливается. Очередь отправляет организатору новости о входе и выборе гостя, гостю — напоминание до дедлайна и результат утверждения, ресторану — сообщение об утверждённом заказе. При изменении параметров банкета присоединившиеся гости получают обновление. Напоминание отменяется после сохранения выбора. Доставка через MAX может задерживаться; отправка внешнему пользователю возможна только если он включил уведомления и не остановил бота.

Административные операции из этого документа доступны и через Mini App, и через HTTP API. Сервер всегда проверяет роль, владение, телефон гостя, статус и актуальность заказа независимо от интерфейса.
